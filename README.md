# othello_complexity.rs

Codes and raw results of the paper "Estimation of the number of legal positions in Othello" (https://ipsj.ixsq.nii.ac.jp/records/2005522 (in Japanese)), presented at IPSJ Game Programming Workshop 2025.

論文「オセロの実現可能局面数の推計」（https://ipsj.ixsq.nii.ac.jp/records/2005522 ）で使用したコードと実験結果です。論文の誤りは[正誤表](https://github.com/u-tokyo-gps-tanaka-lab/othello_complexity_rs/blob/master/%E3%82%AA%E3%82%BB%E3%83%AD%E3%81%AE%E5%AE%9F%E7%8F%BE%E5%8F%AF%E8%83%BD%E5%B1%80%E9%9D%A2%E6%95%B0%E3%81%AE%E6%8E%A8%E8%A8%88_%E6%AD%A3%E8%AA%A4%E8%A1%A8.pdf)にまとめています。


## 概要

8×8オセロにおいて、初期局面から合法手とパスの連続で到達できる局面（到達可能局面）の総数を推計するツール群です。

到達可能な局面は天文学的な数にのぼるため、すべてを数え上げることはできません。本研究では、統計的な標本抽出と到達可能性の判定アルゴリズムを組み合わせて総数を推計します。

### 推計の手順

1. 母集団の定義: 到達可能な局面をすべて含み、かつ総数を厳密に計算できる集合を母集団と定めます。たとえば「中央4マスが黒または白で、残り60マスが空き・黒・白のいずれかであり、手番が黒または白である局面全体」を母集団とします。
2. 無作為抽出: 母集団から局面を一様ランダムに抽出します。
3. 到達可能性の判定: 抽出した各局面について、初期局面から到達できるかを判定します。
4. 区間推定: 標本中の到達可能な局面の割合から Wilson 信頼区間を求め、母集団の総数を掛けて到達可能局面数の信頼区間を算出します。

### 判定パイプラインと判定結果

抽出した局面は、計算コストの低い手法から順に4ステージのパイプラインで判定します。前のステージで決着がつかなかった局面だけを次のステージへ渡します。

```text
[抽出した標本]
   │
   ▼
1. フィルタ (Pipeline::filters / run_filters)
   └─ 到達可能局面の必要条件を検査し、違反した局面を「到達不能 (NG)」として除外する。
   │
   │ すべてのフィルタを通過した局面
   ▼
2. 幅優先逆探索による判定 (Pipeline::reverse_search / reverse_search)
   └─ 目標局面から幅優先で逆探索し、合流、探索の完了、登録局面数の上限到達のいずれかまで調べる。
   │
   │ 登録局面数の上限に達した局面 (UNKNOWN)
   ▼
3. SAT による判定 (Pipeline::sat / sat_reachability)
   └─ 初期局面からの着手列が存在するかを SAT ソルバで調べる。
   │
   │ 時間制限などで決着がつかなかった局面 (UNKNOWN)
   ▼
4. 逆探索による判定 (Pipeline::reverse_search / reverse_search)
   └─ 目標局面から後向きにグラフ探索を行い、初期局面側から生成した局面と合流するか調べる。
   │
   ▼
[最終結果: OK / NG / UNKNOWN]
```

各ステージは判定結果に応じて局面を分類し、次の3種類の接尾辞がついたファイルに出力します。フィルタ（`run_filters`）と SAT・逆探索では `_OK` の意味が異なる点に注意してください。

| ファイル接尾辞 | フィルタ (`run_filters`) での意味 | SAT・逆探索での意味 |
|---|---|---|
| `_NG` | 到達不能が証明された。必要条件を満たさない。 | 到達不能が証明された。初期局面からの着手列が存在しない。 |
| `_OK` | 到達可能かは未確定である。そのフィルタの必要条件を満たしたに過ぎず、到達可能の証明ではない。 | 到達可能が証明された。初期局面からの着手列が見つかり、再生検証に成功した。 |
| `_UNKNOWN` | 出力されない。 | 到達可能かは未確定である。制限時間や探索ノード数の上限に達したか、制限付きの探索で棋譜が見つからなかった。 |

### 判定モード

モードは2つあり、局面の対称性や手番を同一視するかどうかが異なります。どちらのモードでも、推計に必要な母集団の総数を厳密に計算できます。

| モード | 到達可能性の判定対象 | 推計の対象 |
|---|---|---|
| `exact` | 指定された局面そのもの（1通り） | 到達可能な局面数 |
| `equivalence` | 盤面の回転・反転8通りと、手番・石色の同時反転2通りを組み合わせた最大16通りのいずれか（ゲーム理論的同値類） | 到達可能な同値類数 |

`exact` モードの母集団は、中央4マスが黒または白で、残り60マスが空き・黒・白のいずれかであり、手番が黒または白である局面全体（2^5 × 3^60 個）です。`equivalence` モードの母集団は、そのうち手番が黒の局面全体（2^4 × 3^60 個）です。

`equivalence` モードでは、抽出した局面のうち同値類の代表局面だけを判定します。代表局面とは、同値類に属する黒番の局面のうち、石のあるマスと手番側の石の配置で比べて最小のものです。各同値類に代表局面はちょうど1つあるので、到達可能な同値類の数は、母集団のうち到達可能な同値類に属する代表局面の数に等しくなります。代表局面でなかった局面は判定しませんが、割合の分母である標本の大きさには含めます。

- 推計パイプラインでは、標本の母集団（`Population::Absolute` または `Population::Classes`）からモードが自動的に決まります。
- 単体コマンド（`gen_random_boards`、`sat_reachability`、`reverse_search`、`verify_record`）では `--mode` オプションで指定します。`run_filters` には `--mode` オプションがありません。


## ビルド環境の準備

線形計画法ソルバ HiGHS と SAT ソルバ Kissat のソースコードはリポジトリに含まれており、`cargo build` 時に自動でコンパイルされます。`highs-sys` のビルドには `cmake` を使うため、事前に `cmake` をインストールして PATH を通しておいてください。

```sh
cargo build --release
cargo test
```

### メモリの設定

本リポジトリはメモリアロケータに mimalloc を使います。次の2つの環境変数を使うと、最大常駐メモリを減らせます。どちらも判定の手順には影響しません。

`MIMALLOC_PURGE_DELAY=0` は、解放したメモリをすぐ OS へ返します。`MIMALLOC_ALLOW_THP=0` は、Linux の透過的巨大ページ（THP）をそのプロセスで無効にします。無効にすると、大きな探索が遅くなることがあります。

どちらも `.cargo/config.toml` に設定されているため、`cargo run` と `cargo test` では自動で有効になります。`target/release/` のバイナリを直接実行するときは自動で有効にならないため、`MIMALLOC_PURGE_DELAY=0 MIMALLOC_ALLOW_THP=0 target/release/reverse_search ...` のように指定してください。速度を優先して THP を使うときは、`MIMALLOC_ALLOW_THP=1 cargo run --release --bin reverse_search -- ...` のように指定すると、`.cargo/config.toml` の値を上書きできます。


## 到達可能局面数の推計（基本手順）

推計は、標本の抽出から信頼区間の算出までを `estimate::Pipeline` のメソッドチェーンとして記述し、1つの Rust プログラムとして実行します。

以下は、`equivalence` モードで大きさ 1,000 の標本を抽出し、到達可能な同値類数の 99.5% 信頼区間を求める例（`examples/estimate.rs`）です。標本のうち判定する代表局面は、およそ 125 件です。

```rust
use std::path::Path;
use std::time::Duration;

use othello_complexity_rs::estimate::{Pipeline, SampleSpec, SatStage};
use othello_complexity_rs::filters::sat::{SatEncoding, SatPortfolio};
use othello_complexity_rs::sampling::Population;
use othello_complexity_rs::search::Strategy;

fn main() -> Result<(), Box<dyn std::error::Error>> {
    let report = Pipeline::sample(SampleSpec {
        population: Population::Classes,
        discs: None,
        sample_size: 1_000,
        seed: 20261022,
    })
    .filters()
    .reverse_search(Strategy::Bfs {
        discs: 10,
        max_nodes: 4_000_000,
        use_lp: false,
        threads: 1,
        parallel_goals: 20,
    })
    .sat(SatStage {
        encodings: SatPortfolio::new(vec![
            SatEncoding::NoPassWitness,
            SatEncoding::PlacementRays,
        ])?,
        seeds: 1,
        parallel_goals: 10,
        timeout: Some(Duration::from_secs(120)),
    })
    .reverse_search(Strategy::GbfsParallel {
        discs: 10,
        max_nodes: 10_000_000,
        use_lp: false,
        threads: 1,
        parallel_goals: 20,
    })
    .run(Path::new("out/estimate"), 0.005)?;
    println!("{}", report.interval);
    Ok(())
}
```

この例は次のコマンドで実行できます。実際の実験プログラムは、後述の「実験プログラムの置き場所」のとおり `src/bin/` に置きます。

```sh
cargo run --release --example estimate
```

パイプラインは次のように動作します。

- 宣言と実行の分離: `filters`、`sat`、`reverse_search` の各メソッドは判定ステージを登録するだけです。実際の計算は、末尾の `run` を呼んだ時点で始まります。
- 実行前の設定検査: `run` は計算を始める前に全ステージの設定値を検査します。不正な値があれば、出力先に何も書き出さずにエラーで終了するため、途中のステージまで時間をかけて計算した後に設定ミスで止まることはありません。
- ステージ間の引き継ぎ: 各ステージは、前のステージで未確定（`UNKNOWN`）として残った局面だけを判定します。ステージの順序や回数は自由に組めます。たとえば `sat` を2回並べると、後述の「`nopass-witness` を使った2段階の SAT 判定」になります。

### 1. 標本の指定

パイプラインの起点には、新しく標本を抽出する `Pipeline::sample` か、既存の標本を読み込む `Pipeline::from_sample_dir` のいずれかを指定します。

- `Pipeline::sample(SampleSpec { .. })`: 母集団から指定した大きさの標本を一様に復元抽出し、出力ディレクトリの `sample/` に `positions.txt` と `sampling.json` を書き出します。`equivalence` モードでは、代表局面だけを `positions.txt` に書きます。
- `Pipeline::from_sample_dir(&Path)`: `gen_random_boards` または `convert_boards` で作成済みの標本ディレクトリを読み込みます。

`SampleSpec` の各フィールドは次のとおりです。

| フィールド | 意味 |
|---|---|
| `population` | 母集団を指定する。`Population::Absolute` は `exact` モード、`Population::Classes` は `equivalence` モードに対応する。 |
| `discs` | 母集団を特定の石数の局面に限定する場合は `Some(n)`、全石数を対象とする場合は `None` を指定する。 |
| `sample_size` | 標本の大きさ、すなわち母集団から一様に復元抽出する局面の数を指定する。`exact` では抽出した局面がすべて `positions.txt` に書かれる。`equivalence` では代表局面だけが書かれ、その行数は標本の大きさのおよそ8分の1になる。 |
| `seed` | 乱数シードを指定する。値は `sampling.json` に記録され、同じシードを指定すれば同じ標本を再現できる。 |

### 2. 判定ステージの追加

標本に対して、以下のメソッドで判定ステージを追加します。

| メソッド | 判定の内容 |
|---|---|
| `filters()` | 4種類のフィルタを順に適用し、到達可能局面の必要条件を満たさない局面を `NG` とする。通過した局面は `UNKNOWN` のまま次のステージへ渡る。 |
| `sat(SatStage { .. })` | SAT ソルバで初期局面からの着手列を探す。 |
| `reverse_search(Strategy::..)` | 目標局面から後向きに探索し、初期局面側から生成した局面と合流するか調べる。 |
| `equivalence_ng(&Path)` | 指定した `equivalence` モードの推計で `NG` と判定された同値類に属する局面を `NG` とする。`exact` モードの標本でだけ使える。詳細は後述の「7. 同値類の推計を流用した局面数の推計」で説明する。 |

#### `filters()` で適用されるフィルタ

| フィルタ名 | 検査する到達可能局面の必要条件 |
|---|---|
| `con` | 石のあるマスが縦・横・斜めに隣接し、1つの連結成分になっているか。 |
| `occupancy` | 石の色を無視したとき、「既存の石が2つ並んでいる隣にしか新しい石を置けない」という緩和した着手条件のもとで、初期配置の4石から目標局面の全石まで1石ずつ配置できるか。 |
| `never_flipped` | `occupancy` の条件に加え、各石を置いた時点で相手の石を挟める方向が存在するか。さらに、最終局面から一度も返っていないと証明できる石の着手順序と色が矛盾しないか。 |
| `lp` | 石の配置と反転関係を変数とする線形計画問題（LP）に実行可能解が存在するか。 |

#### `sat(SatStage { .. })` の設定項目

設定値に既定値はないため、すべてのフィールドを明示します。

| フィールド | 意味 |
|---|---|
| `encodings` | SAT への符号化方式を指定する。`SatEncoding::Ply.into()` のように1つの方式を指定するか、`SatPortfolio::new(vec![..])` で複数の方式を組み合わせる。各方式の詳細は後述の「SAT 判定の詳細仕様」で説明する。 |
| `seeds` | 1つの符号化方式につき、乱数シードを変えてソルバを実行する回数を指定する。 |
| `parallel_goals` | 同時に判定する局面数を指定する。 |
| `timeout` | 候補局面1つに対する SAT ソルバの制限時間を指定する。ポートフォリオの全ワーカーが CNF を Kissat に読み込んだ時点から測る。`None` なら制限時間を設けない。`equivalence` モードでは、標準の初期局面を固定する対称変換で候補をまとめるため、1つの入力局面につき最大4通りの対称局面を個別に解く。したがって、1局面あたりの合計時間は指定値を超えることがある。 |

#### `reverse_search(Strategy::..)` の設定項目

逆探索の方式は `Strategy` の7つの列挙子から選びます。列挙子とフィールドは、単体コマンド `reverse_search` のサブコマンドおよびオプションに対応します（例: `Strategy::DfsParallel` は `dfs-parallel` に対応）。

`Strategy::Bfs` と `Strategy::GbfsParallel` では、`threads` が1局面の探索に使うワーカースレッド数、`parallel_goals` が同時に探索する局面数です。単体コマンドの対応するオプションは `--threads` と `--parallel-goals` であり、どちらも既定値は1です。`parallel_goals` を2以上にする場合は、`threads` に1以上を指定し、両者の積を64以下にしてください。

`gbfs-parallel` の概算メモリ使用量は「`parallel_goals` × 1局面のピーク」です。探索上限が大きい場合、1ノードあたりのメモリ使用量は約90 Bが目安です。多数の局面を処理するときは、`threads` を小さくし、利用可能な計算資源とメモリの範囲で `parallel_goals` を大きくすると、単位時間あたりに処理できる局面数を増やしやすくなります。

### 3. 出力ディレクトリの構成と仕様

`run(out_dir, alpha)` を実行すると、`out_dir` に指定した出力ディレクトリに以下のファイル群が書き出されます。

```text
out/estimate/
├── sample/                 Pipeline::sample で抽出した標本
├── 01-filters/             con_OK.txt、con_NG.txt、…、lp_OK.txt、lp_NG.txt
├── 02-reverse-search/      reverse_equivalence_OK.txt、_NG.txt、_UNKNOWN.txt、_records.csv
├── 03-sat/                 sat_equivalence_OK.txt、_NG.txt、_UNKNOWN.txt、_records.csv
├── 04-reverse-search/      reverse_equivalence_OK.txt、_NG.txt、_UNKNOWN.txt、_records.csv
└── summary.json            推計全体の設定と各ステージの結果記録
```

- 各ステージのディレクトリ（`01-filters/` など）: 宣言順の2桁の番号とステージ種別をつないだ名前になります。SAT ステージと、`parallel_goals` が2以上の `bfs` または `gbfs-parallel` では、判定が完了した局面から順にファイルへ追記されるため、出力行の並び順は入力順とは一致しません。
- `_records.csv`: 到達可能と判定された `OK` の局面について、到達手順（棋譜）が記録されます。完了順で出力される場合は、CSV の行番号ではなく `input_index` で入力局面に対応付けます。棋譜は後述の `verify_record` コマンドで独立に検証できます。
- `summary.json`: 標本の情報、有意水準（`alpha`）、および各ステージの設定値・完了状態・判定件数・そのステージ終了時点での信頼区間が記録されます。ステージが1つ完了するたびに更新されるため、実行が途中で止まっても完了したステージまでの結果が残ります。

出力ディレクトリを指定する際は、以下の点に注意してください。

- 既存のディレクトリを指定した場合、推計が出力するファイルと同名のファイルだけが上書きされ、それ以外のファイルは残ります。
- 入力データの破損を防ぐため、標本ディレクトリと、後述する `from_run` が引き継ぐ元の実行ディレクトリは出力先に指定できません。元の実行がさらに分岐している場合は、その先にあるすべての実行ディレクトリも指定できません。
- `run_filters` などの単体コマンドでは、出力先（`--out-dir`）に推計の出力ディレクトリやその直下のサブディレクトリを指定できません。

### 4. 推計結果の見方

`run` の戻り値（`report.interval`）には、最終ステージ終了時点での集計件数と信頼区間が格納されます。`examples/estimate.rs` では次のように表示されます。

```text
Population size = 678258532403459256228710931216
Sample size = 1000
Observed reachable fraction range: [0.000000000000, 0.000000000000]
99.5% approximate Wilson CI: [0.000000000000, 0.007817838399]
Expected |R| interval: [0.000000e+0, 5.302516e+27]
```

- `Population size`: 母集団の総数です。
- `Sample size`: 標本の大きさです。`equivalence` モードでは代表局面でなかった局面も含むので、`positions.txt` の行数より大きくなります。
- `Observed reachable fraction range`: 標本の大きさに占める `OK` の件数の割合を、範囲で示したものです。`equivalence` モードの `OK` は、代表局面であり、その同値類に到達可能な局面があると判定した行です。下端は未確定（`UNKNOWN`）をすべて到達不能とみなした場合、上端はすべて到達可能とみなした場合の割合です。
- `Expected |R| interval`: `exact` モードでは到達可能な局面数、`equivalence` モードでは到達可能な同値類数の信頼区間です。
  - 下端: `UNKNOWN` をすべて到達不能とみなしたときの Wilson 信頼区間の下端 × 母集団の総数で算出します。
  - 上端: `UNKNOWN` をすべて到達可能とみなしたときの Wilson 信頼区間の上端 × 母集団の総数で算出します。

信頼水準は `run(out_dir, alpha)` の第2引数である有意水準 `alpha` で決まります。例の `0.005` は 99.5% 信頼区間に対応します。

### 5. 中断した推計の再開とステージの追加

すでに `summary.json` が存在する出力ディレクトリに対して `run` を呼ぶと、完了済みステージの出力ファイルを読み込んで検証し、未完了のステージから実行を再開します。現在の保存形式と一致しない結果は再開できません。

再開できるのは、プログラムで指定した標本および先頭ステージ群の設定が、保存済みの完了ステージと一致している場合です。一致しない場合は、ディレクトリを変更せずにエラーで終了します。最初からやり直す場合は、別の出力ディレクトリを指定してください。

この仕組みを使って、以下の3通りの操作を行えます。

1. 中断した推計の再開: 途中で止まったプログラムをそのまま再実行すると、未完了のステージから再開します。未完了だったステージは最初からやり直しますが、外部メモリ BFS ステージに限っては `resume: true` と前回と同じ `tmp_dir` を指定するとステージの途中から再開できます。
2. 後続ステージの追加: 完了した推計プログラムのメソッドチェーン末尾に新しいステージを足して再実行すると、追加したステージだけが実行されます。たとえば、SAT ステージで残った `UNKNOWN` に対し、探索上限を引き上げた逆探索ステージを追加できます。
3. 有意水準の変更: `run` の第2引数（`alpha`）だけを変更して再実行すると、判定ステージを再実行せずに信頼区間だけを再計算します。

### 6. 途中ステージからの分岐 (`Pipeline::from_run`)

`Pipeline::from_run(&Path, k)` を使うと、既存の推計結果から完了済みの先頭 `k` ステージを引き継ぎ、後続ステージの設定を変えた推計を実行できます。標本と先頭 `k` ステージの出力はコピーせず、初回実行と再開のたびに元の実行ディレクトリから読みます。分岐先に作成されるのは、`summary.json` と分岐後に追加したステージのディレクトリだけです。

以下の例は、`out/estimate` の第3ステージ（SAT）までの結果を引き継ぎ、逆探索の方式と上限を変えた推計を `out/estimate-gbfs` で実行します。

```rust
Pipeline::from_run(Path::new("out/estimate"), 3)
    .reverse_search(Strategy::GbfsParallel {
        discs: 10,
        max_nodes: 10_000_000,
        use_lp: false,
        threads: 1,
        parallel_goals: 20,
    })
    .run(Path::new("out/estimate-gbfs"), 0.005)?;
```

引き継ぎ元のディレクトリである `out/estimate` は変更されません。ただし、分岐は実行のたびに元の標本とステージ出力を参照するため、元の実行ディレクトリを削除または移動すると実行できなくなります。元が別の分岐である場合は、その参照先も同様に保持してください。

`from_run` に相対パスを渡した場合、そのパスはプロセスの作業ディレクトリから解決されます。分岐を重ねる場合は、途中の `summary.json` に記録された相対パスも同じ基準で解決されるため、すべての分岐を同じ作業ディレクトリから作成して実行してください。

分岐先には `sample/` が作成されません。分岐した推計の標本を `convert_boards` に渡す場合、生成した標本では、その標本を持つ祖先の実行ディレクトリにある `sample/` を指定します。外部の標本ディレクトリから始めた推計では、`summary.json` の `sample.source.directory` に記録されたディレクトリを指定します。

### 7. 同値類の推計を流用した局面数の推計 (`convert_boards`、`equivalence_ng`)

`equivalence` モードの推計を終えた後、その標本と判定結果を流用して、`exact` モードの推計（到達可能な局面数の推計）を行えます。手順は2段階です。まず同値類の標本を局面の標本に変換し、次に変換した標本で推計を実行します。このとき、同値類の推計で `NG` と判定された局面は判定し直しません。

#### 標本の変換

`convert_boards` は、`equivalence` モードの標本ディレクトリを読み、`exact` モードの標本ディレクトリを書き出します。入力には、`Pipeline::sample` が出力した `sample/` か、`gen_random_boards --mode equivalence` の出力を指定します。

```sh
cargo run --release --bin convert_boards -- \
  --sample-dir out/estimate/sample --seed 20261108 \
  --out-dir out/converted
```

- `--seed`: 変換に使う乱数シードを指定します。省略はできません。元の標本と同じシード値を指定するとエラーになります。元の標本と同じ乱数列を使うと、同値類の抽出と変換時の抽選が独立でなくなり、変換後の標本が一様にならないためです。
- 石数を固定した同値類の標本は、同じ石数の局面からなる標本に変換されます。
- 代表局面が1件もない同値類の標本は変換できず、エラーになります。変換しても空の標本しかできないためです。
- 変換後の標本の大きさは、採択した行の数です。元の標本の大きさは引き継ぎません。元の標本で代表局面でなかった局面は変換の対象にならず、変換後の標本に加えた各局面が、局面全体から一様に1回抽出したものにあたるためです。
- 出力ディレクトリには `positions.txt` と `sampling.json` が書き出されます。
- 入力の `positions.txt` と `sampling.json` を、出力先の各ファイルと同じファイルにはできません。シンボリックリンクやハードリンクで同じファイルを指す場合もエラーになります。
- 入力は、本ツールで一様に抽出した同値類の標本であることを前提とします。`convert_boards` は `sampling.json` の記載と、各行が黒番の代表局面であることを検査しますが、標本が実際に一様に抽出されたかどうかまでは検査できません。

変換の仕組みは次のとおりです。同値類の標本の各行には、黒番の代表局面が記録されています。各同値類の代表局面はちょうど1つなので、標本の各行は同値類全体から一様に抽出したものにあたります。まず、各行の代表局面を回転・反転した8通りの像と、それぞれの石の色と手番を同時に交換した像を合わせた16通りから、互いに異なる局面 $m$ 個を一定の順に並べます。次に、0から15の整数を一様に1つ引きます。引いた整数が $m$ 未満ならその行を採択し、その番号の局面を変換後の標本に加えます。$m$ 以上ならその行を棄却し、変換後の標本には何も加えません。

この1回の抽選で、各行が採択される確率は $m/16$ になり、変換後の標本に加わる局面は $m$ 個の像から一様に選ばれます。したがって、どの局面も、属する同値類が引かれる確率と 1/16 の積という同じ確率で変換後の標本に加わり、変換後の標本は局面全体からの一様な標本になります。

もし棄却をせずに、同値類の標本にあるすべての行について $m$ 個の像から1つを選んで変換後の標本に加えると、どの同値類からも局面が1つずつ加わります。すると、ある局面が加わる確率はその同値類の像の数 $m$ に反比例するため、像が16個に満たない自己対称な同値類の局面が過大に抽出されます。

棄却が起こるのは、引いた整数が $m$ 以上のときだけなので、行が棄却される確率は $1 - m/16$ です。$m = 16$ の行は必ず採択されます。$m$ が16未満の行も必ず棄却されるわけではなく、確率 $m/16$ で採択されます。たとえば $m = 8$ の行は、0から7を引けば採択され、8から15を引けば棄却されるので、採択と棄却の確率はともに 1/2 です。$m$ が16未満になるのは自己対称な同値類の行だけです。そうした同値類はごくわずかなので、実際にはほぼすべての行が採択されます。
#### 判定の引き継ぎ

変換した標本で推計するときは、最初のステージとして `equivalence_ng(&Path)` を置き、`equivalence` モードで実行した元の推計の出力ディレクトリを指定します。

```rust
Pipeline::from_sample_dir(Path::new("out/converted"))
    .equivalence_ng(Path::new("out/estimate"))
    .reverse_search(Strategy::Bfs {
        discs: 10,
        max_nodes: 4_000_000,
        use_lp: false,
        threads: 1,
        parallel_goals: 20,
    })
    .sat(SatStage {
        encodings: SatPortfolio::new(vec![
            SatEncoding::NoPassWitness,
            SatEncoding::PlacementRays,
        ])?,
        seeds: 1,
        parallel_goals: 10,
        timeout: Some(Duration::from_secs(120)),
    })
    .run(Path::new("out/estimate-exact"), 0.005)?;
```

このステージは、元の推計で `NG` と判定された同値類に属する局面を `NG` とし、残りの局面を `UNKNOWN` のまま次のステージへ渡します。元の推計で `OK` だった同値類の局面は判定し直します。元の推計が示したのは同値類に属するいずれか1つの局面への到達であり、変換で選んだ局面に到達できるとは限らないからです。

- 元の推計は全ステージを終えている必要があります。また、石数の指定も元の標本と変換した標本で一致している必要があります。
- 変換した標本に含まれる局面の代表局面が元の標本にない場合は、指定した推計が誤っているとしてエラーになります。
- これらの検査はこのステージの実行時に行います。検査に失敗すると、このステージは出力のない未完了のステージとして残ります。`equivalence` モードの標本にこのステージを置いた場合だけは、計算を始める前にエラーになります。
- `filters()` は置かなくて構いません。引き継ぎ後に残る局面は、元の推計でフィルタを通過した同値類の局面です。フィルタは回転・反転と色の交換で結果を変えないので、もう一度適用しても `NG` にはなりません。
- 出力ディレクトリの `01-equivalence-ng/` には、`NG` とした局面の `equivalence_NG.txt` と、次のステージへ渡した局面の `equivalence_UNKNOWN.txt` が入力順に書き出されます。
- このステージが完了した後は、引き継ぎ元の出力ディレクトリがなくても再開や分岐ができます。
- 元の推計の分類と変換した標本の分類を同時にメモリに載せるため、1億行どうしでは見積もりで 30 GB 程度のメモリを要します。

### 8. 実験プログラムの置き場所 (`src/bin/`)

本番の推計は、1実験あたり1バイナリとして `src/bin/<名前>.rs` に作成します。中身は、「到達可能局面数の推計（基本手順）」の例と同じく、標本の指定から `run` までを1つのメソッドチェーンとして書いた `main` 関数です。

`src/bin/` の直下に置いた `.rs` ファイルは Cargo が自動でバイナリとして登録するので、`Cargo.toml` を編集する必要はありません。サブディレクトリに置くと登録されないので、必ず直下に置いてください。リポジトリのルートから以下のコマンドで実行できます。

```sh
cargo run --release --bin <名前>
```

運用時は以下の点に注意してください。

- 推計が完了したら、再現性を保つために実験プログラム（`.rs` ファイル）を出力ディレクトリと一緒に保存してください。
- 実験プログラムは、`cargo build` や `cargo test` のたびにほかのコードと一緒にコンパイルされます。ライブラリの仕様変更により古い実験プログラムがコンパイルできなくなったら、その時点で修正するか削除してください。過去の実験は、保存したプログラムと当時のライブラリから再現できます。


## SAT 判定の詳細仕様

### 符号化方式

初期局面から目標局面へ至る盤面の推移を、どのような論理式で表すかを指定します。複数の方式を並べると、候補局面ごとに全方式の論理式を作って同時に解きます。再生検証を通った棋譜が見つかるか、到達不能を証明できる方式が解なしと判定した時点で、残りの求解を打ち切ります。結論は、すべてのソルバの報告を受け取り、エラーや矛盾する結果がないことを確かめてから返します。

- 推計パイプライン（`SatStage` の `encodings`）:
  - 単一方式: `SatEncoding::Ply.into()`
  - 複数方式: `SatPortfolio::new(vec![SatEncoding::NoPassWitness, SatEncoding::PlacementColumns])?`
- 単体コマンド（`sat_reachability` の `--encoding`）:
  - 単一方式: `--encoding ply`
  - 複数方式: `--encoding nopass-witness+placement-columns`（`+` で連結）

以下では用語を次のように使い分けます。
- 着手: 石を置くこと、またはパスをすることです。
- 着石: 石を置くことであり、パスは含みません。
- 層: 着手列の途中における、ある1時点の盤面を表す変数の組です。
- 節: SAT の制約を構成する論理和（OR 節）の1つです。

| 方式 | 符号化の仕組み | 解なし（UNSAT）のとき |
|---|---|---|
| `ply` | 着手1回ごとに層を1つ置く。 | 到達不能（`NG`）と確定する。 |
| `placement-columns` | 着石1回ごとに層を1つ置く。各着石の直前に強制パスを最大1回、最後の着石後にもパスを最大1回挟めるようにする。石を挟む並びは、着石するマス、方向、挟む枚数の組ごとに列挙する。加えて、「初期局面で空いており目標局面で石がある各マスへ、全層を通じてちょうど1回着石する」という列方向の制約を課す。この制約は合法な着手列が必ず満たす性質を明示したもので、判定結果は変えずにソルバの探索を助ける。 | 到達不能（`NG`）と確定する。 |
| `placement-rays` | `placement-columns` と同等の層構成・制約を持つが、石を挟む条件を隣接マス間で共有して節数を減らす。各層の着石者を変数で表すことでパスを表現する。 | 到達不能（`NG`）と確定する。 |
| `nopass-witness` | パスを一度も含まず、黒白が交互に着石する着手列に限定して探索する。反転条件を隣接マス間で共有して式を小さくする。 | 未確定（`UNKNOWN`）のままとする。単独実行時は `_NG` ファイルが常に空になる。 |

オセロでは一度置かれた石が盤面から取り除かれないため、目標局面で空いているマスは途中のどの時点でも空いています。すべての方式でこの性質を利用し、空きマスへの着石や反転を表す変数・節を省略して論理式を小さくしています。ただし、パスできるかどうかの判定にはそのマスへ打てるかの情報が必要なため、合法手判定の変数・節は残しています。

### 幅優先逆探索

`Strategy::Bfs` は、目標局面から石数ごとに幅優先で逆探索し、初期局面側から生成した前向き局面表との合流を調べます。前向き局面表に合流した場合は `OK` と判定し、復元した棋譜を合法手規則で再生検証します。先行局面を列挙し尽くした場合は `NG`、登録局面数が `max_nodes` を超えた場合は `UNKNOWN` と判定します。

`discs` は前向き局面表の石数、`max_nodes` は1回の探索で登録する局面数の上限です。`use_lp` は線形計画法による枝刈りの有無を指定し、標準の初期局面から探索するときだけ適用されます。`threads` は1局面の層を処理するスレッド数、`parallel_goals` は同時に探索する局面数です。

`summary.json` の `nodes` には、そのステージへ入力されたすべての局面について、`OK`、`NG`、`UNKNOWN` のいずれであっても値が入力順に格納されます。`nodes[i]` の添字 `i` は0から始まり、その値は入力順で `i + 1` 番目の局面に対応します。たとえばフィルタの直後に実行するステージでは、入力は `01-filters/lp_OK.txt` の局面であり、そのファイルの順序が入力順になります。この入力には重複する局面がありません。一方、`parallel_goals` が2以上の場合、ステージの `_OK.txt`、`_NG.txt`、`_UNKNOWN.txt` は判定の完了順に出力されるため、これらの行番号を `nodes` の添字として使うことはできません。

探索を尽くして `NG` と判定された局面では、対応する `nodes` がその局面を `NG` にできる最小の `max_nodes` を表します。ある上限で `NG` になる局面数を求めるときは、そのステージの `_NG.txt` に記載された局面だけを入力順の位置へ対応付け、`nodes` がその上限以下である局面を数えます。

### 応用例: `nopass-witness` を使った2段階の SAT 判定

`nopass-witness` はパスのある手順を見落とすため到達不能（`NG`）の証明には使えませんが、パスなしで到達できる局面は短時間で見つけて `OK` と判定できます。これを完全な方式の前段に挟むと、全体の実行時間を短縮できます。推計では、1つのパイプラインに `sat` ステージを2つ並べます。

```rust
Pipeline::sample(spec)
    .filters()
    // 第1ステージ: パスなしの到達手順を1秒だけ探す。見つかった局面だけが OK になり、残りは UNKNOWN のまま次のステージへ渡る
    .sat(SatStage {
        encodings: SatEncoding::NoPassWitness.into(),
        seeds: 1,
        parallel_goals: 2,
        timeout: Some(Duration::from_secs(1)),
    })
    // 第2ステージ: 残った局面を完全な方式で判定する
    .sat(SatStage {
        encodings: SatEncoding::Ply.into(),
        seeds: 1,
        parallel_goals: 2,
        timeout: Some(Duration::from_secs(10)),
    })
    .run(Path::new("out/estimate"), 0.005)?;
```


## 単体コマンドによる個別判定

推計パイプラインを通さずに、特定の局面や局面ファイルを個別に判定・検証するコマンド群です。

### 標本の単体抽出 (`gen_random_boards`)

`Pipeline::sample` と同じ手順で標本を抽出し、標本ディレクトリに書き出します。書き出した標本は `Pipeline::from_sample_dir` で推計に使えます。母集団を特定の石数の局面に限定する場合は `--discs` を指定します。

```sh
cargo run --release --bin gen_random_boards -- \
  --mode equivalence --sample-size 1000 --seed 20261022 \
  --out-dir out/sample
```

### フィルタの単体実行 (`run_filters`)

指定した1種類のフィルタだけを実行します。複数のフィルタを順に適用したい場合は、出力された `_OK` ファイルを次のフィルタの入力に指定してください。

```sh
cargo run --release --bin run_filters -- con out/estimate/sample/positions.txt -o out/con
```

### SAT の単体実行 (`sat_reachability`) と棋譜の検証 (`verify_record`)

`--goal` で指定した1つの局面、または `--goal-file <PATH>` で指定したファイル内の局面群を SAT ソルバで判定します。`--from-initial` は標準の初期局面からの到達可能性を判定するフラグです。

```sh
# 1局面を直接指定して判定
cargo run --release --bin sat_reachability -- --from-initial --mode exact \
  --encoding ply \
  --goal '-------------------O-------OO------OX--------------------------- w' \
  --parallel-goals 1 --sat-timeout-secs 10 \
  --out-dir out/sat_d3

# 出力された到達手順（棋譜）が合法かどうかを独立に検証
cargo run --release --bin verify_record -- \
  --input-file out/sat_d3/sat_exact_records.csv
```

### 逆探索の単体実行 (`reverse_search`)

局面ファイルに対して逆探索を実行します。次の例では、4局面を同時に処理し、各局面の探索に1スレッドを使います。

`--max-nodes` は、`exact` では完全一致の候補ごとに、`equivalence` では入力局面ごとに適用されます。DFS では訪問した局面数、BFS と GBFS では登録した局面数を制限します。

```sh
cargo run --release --bin reverse_search -- gbfs-parallel \
  out/estimate/03-sat/sat_equivalence_UNKNOWN.txt \
  --mode equivalence \
  --discs 8 --max-nodes 10000 --threads 1 --parallel-goals 4 \
  --out-dir out/reverse_search
```


## 局面データの書式と旧データの変換

### 局面の表記形式（66文字形式）

本リポジトリの判定ツールは、盤面64文字 + 空白1文字 + 手番1文字（`b` または `w`）の計66文字で1局面を表します。

```text
---------------------------OX------XO--------------------------- b
```

- マスの並び順: 左上から1行ずつ走査し、A1〜H1、A2〜H2、…、A8〜H8 の順に並べます。
- マスの記号: 手番側から見た相対表記で、それぞれ次の状態を表します。
  - `X`: 手番側の石を表します。
  - `O`: 相手側の石を表します。
  - `-`: 空きマスを表します。
- 手番の記号: `b` が黒番、`w` が白番を表します。
- `X` と `O` は黒・白という絶対的な色ではなく、手番側から見た相対表記です。たとえば手番が `w`（白番）の行では、`X` が白石、`O` が黒石を表します。

### 手番のない64文字データ

過去の研究データ（`result/` 内のファイルなど）には、手番情報を持たない64文字の盤面データがあります。判定ツールに入力するには、手番を補って66文字形式に変換する必要があります。これらのデータには抽出条件を記録した `sampling.json` がないので、推計の標本としては使えません。

個別の局面を判定するだけなら、ファイル内の記号の取り決めを確認した上で、行末に空白と手番を直接付与できます。たとえば各行の `X` が黒番における手番側の石を表しているファイルであれば、以下のコマンドで変換できます。`X` が手番側の石を表していないファイルでは、`X` と `O` の入れ替えも必要です。

```sh
sed 's/$/ b/' boards.txt > positions.txt
```
