# 逆探索のビームサーチ評価

2026年10月25日に、`performance-enhancement` の GBFS と、評価関数を使うビームサーチを比較した。**今回検証したビームサーチは、同じ成功数を保ちながら時間と探索量を減らす汎用的な置き換えにはならなかった。** 実装は実験用の追加方式として提供する。

ビーム単独では短時間で終了するが、独立した96局面では GBFS が54局面を解いたのに対し、採用候補の `mobility` は29局面しか解かなかった。未解決分に GBFS を適用すると成功数は54に戻るものの、生成候補数は約1.24%増えた。実際の2段階の CLI 実行でも、時間の明確な改善は確認できなかった。過去の SAT 実験から取り出した58局面には、追加の解を発見できなかった。

## 比較した実装

基準は `performance-enhancement` の [`9208dbd0f1981389de8086bdeb52490e56561226`](https://github.com/u-tokyo-gps-tanaka-lab/othello_complexity_rs/commit/9208dbd0f1981389de8086bdeb52490e56561226) にある GBFS である。`master` からは絶対手番、証明棋譜、必要条件、逆着手列挙なども変わっているため、旧版との数値を探索方式だけの差として比較していない。GBFS には生成数・展開数・候補保持数の計測を追加したが、優先順位と登録局面数による停止条件は保った。

[新しい探索実装](../../src/search/beam.rs)は、以下の2方式を提供する。

1. 層ごとのビームサーチは、石数が同じ候補から上位のものだけを保持し、その層の展開が終わってから次の石数へ進む。ベンチマークの `beam-*` がこの方式である。
2. Best-first ビームサーチは、残り石数が少ない候補を第1優先とし、同じ石数では評価関数で順位を付ける。上位の候補をすぐ展開するので、層全体を走査する必要がない。CLI の `beam` と、ベンチマークの `best-first-*` がこの方式である。

両方式は、幅を超える候補を逐次捨てる。逆着手は遅延列挙し、候補の採択が決まったときだけ証明手順をコピーする。Best-first 方式は、完全に展開し終えた局面を4096件の固定キャッシュに記憶する。ハッシュが衝突しても完全な `Position` が一致しない限り省略せず、退避された局面は必要なら再探索する。

Best-first 方式の待機候補は最大で幅の値に等しく、展開中の1局面を加えた `peak_frontier` は幅32なら33以下になる。これはプロセス全体のメモリ量ではなく、前向き表、必要条件のキャッシュ、既展開キャッシュを除く候補数である。

### 評価関数

同じ石数の候補に対し、次の5種類を試した。どれも順位付けのための評価であり、到達可能性の証明条件ではない。

| 値 | 評価 |
|---|---|
| `branching` | 逆着手の分岐数を小さい順に並べる。基準の GBFS と同じ。 |
| `mobility` | 両者の前向き合法手数の合計を大きい順に並べる。 |
| `coherence` | 各色の縦横斜めの同色隣接辺数を $E_p,E_o$ として、$(E_p+1)(E_o+1)$ を大きい順に並べる。 |
| `continuation` | `coherence` に、必要条件を満たす逆着手マス数を1増やして掛ける。 |
| `frontier` | 占有マスクが含まれる前向き境界局面について、絶対色の不一致数を $m$ とした $2^{-m}$ の合計を大きい順に並べる。 |

`mobility` の式は、合法手集合を $L$ として次のとおりである。Best-first 方式では、この値の比較より先に石数を比較する。

\[
h(s)=|L(P_s,O_s)|+|L(O_s,P_s)|.
\]

`continuation` は必要条件の計算前に未制約の逆着手マス数で評価の上限を計算し、その上限でも保持できない候補の検査を省く。`frontier` は色の不一致を絶対色で計算し、浮動小数点の加算順に結果が依存しないよう整数で実装した。

### 判定の健全性

幅制限で候補を捨てた後の失敗は `UNKNOWN` であり、`NG` ではない。前向き表との一致は幅制限より先に検査する。解を発見した場合は、初期局面から目標局面までの証明棋譜を再生する。逆パスは開始局面と各逆着手候補で別に処理し、手番を含む完全な局面を重複判定に使う。

既展開キャッシュは部分的に展開した局面を登録しない。幅制限の履歴は問い合わせ全体で保持するため、キャッシュを使った後でも、候補を捨てた探索の失敗を到達不能と誤判定しない。探索上限にちょうど達した場合は、最後の候補で実際には列挙し終えていても、保守的に `UNKNOWN` とすることがある。

## 条件の選択と独立検証

調整には seed `20261025` の合法な40局面を使った。16、24、32、40、48石の局面を各8件生成し、方式、評価関数、幅、生成上限を比較した。評価関数 `mobility`、幅32、生成上限100,000を選び、**設定を固定してから** seed `20261026` を使う独立検証へ進んだ。独立検証の結果を使った再調整は行っていない。

調整用の40局面では、`mobility` のビームを前段に置くと、GBFS 単独の27成功を維持して、生成数を約11.4%、個別時間の合計を約12.6%減らせた。しかし、以下の独立検証では再現しなかった。調整時の値だけを改善結果として採用していない。[調整時の生データ](tuning.csv)と[生成上限10,000の比較](tuning_small_budget.csv)も保存した。調整中の正確なソース指紋は取得していないことを、メタデータに記載している。

主検証は `exact` モード、前向き境界8石、1スレッド、3反復で行った。独立した96局面は、16、24、32、40、48、56石を各16件含む。各石数の生成に ChaCha8 の固定シードを使い、生成元の棋譜と発見された棋譜をそれぞれ検証した。実行順は局面と反復ごとにずらした。

GBFS の上限100,000は登録した相異なる局面数であり、ビームの上限100,000は生成候補数である。同じ数値を同じ単位の予算として扱っていない。表の「生成数」は、両方式とも重複と必要条件による棄却を含む逆着手・逆パス候補数を表し、開始局面は含めない。「展開数」は、逆着手候補の列挙を開始した局面数である。

実行環境は AMD EPYC 9V74、Linux x86-64、Rust 1.99.1、`cargo build --release --locked` で、既存の `lto = true` を使用した。詳細と SHA-256 は [benchmark_metadata.json](benchmark_metadata.json) と [environment.json](environment.json) に記録した。3反復の時間差に対する統計的有意性は主張しない。

## 独立96局面の結果

生成数と展開数は1反復分で、判定とカウンタは3反復で一致した。時間は、各反復の96局面の探索時間を合計した値の中央値である。この個別探索の時間には、共有の前向き表を構築する時間を含めない。

| 手法 | 到達可能と証明した局面 | 生成数 | 展開数 | 探索時間 | 最大候補数 |
|---|---:|---:|---:|---:|---:|
| GBFS | 54 / 96 | 13,464,464 | 4,744,612 | 11.489秒 | 25,665 |
| Best-first beam、`branching`、幅32 | 30 / 96 | 880,308 | 270,459 | 0.511秒 | 33 |
| Best-first beam、`mobility`、幅32 | 29 / 96 | 663,962 | 213,011 | 0.362秒 | 33 |

速さだけを比較するとビームが優れて見えるが、`mobility` は GBFS の54成功のうち29成功しか得ていない。また、独立検証では `mobility` が `branching` より多く解いたわけでもない。したがって、単独の時間差を同じ問題に対する性能向上と解釈できない。

`mobility` が `UNKNOWN` を返した67局面だけを GBFS に渡すと、成功数は54に戻る。この二段法の生成数は13,631,923、展開数は4,778,592であり、GBFS 単独に対してそれぞれ1.24%、0.72%増える。独立計測時間を加算した推計値は約0.47%短いが、実際のパイプライン時間とは異なる。

16、24、32石では二段法の生成数が減り、40、48、56石では増えた。これは検証後の層別分析であり、「32石以下だけビームを使う」という新しい方針の独立検証ではない。調整と同じ16〜48石の80局面だけを集計しても、生成数は約0.49%増えるため、56石を追加したことだけが負結果の理由ではない。

## 過去の SAT 残存58局面

入力は、既存の `result/thesis_layer_sat/layer_sat_UNKNOWN.txt` の全58行を、選別せず元の順序で使った。旧形式は手番のない64文字なので、各行に ` b` を付け、新しい `exact` の問い合わせとして評価した。元の `UNKNOWN` を現在の正解ラベルには使っていない。石数は45〜56である。[変換の記録](legacy_sat_provenance.json)と[入力](legacy_sat_positions.txt)を保存した。

GBFS、`branching` のビーム、`mobility` のビームのすべてが、全58局面について `UNKNOWN` を返した。この設定で到達不能が証明されたという意味ではない。

GBFS の生成数は17,018,567で、`mobility` の前段は追加で400,410候補を生成した。二段法は17,418,977候補となり、約2.35%増える。追加で解決した局面はなく、独立計測時間の合計も約1.63%増えた。

## CLI 全体の実測

個別探索の時間を足すだけでなく、`reverse_search` を実際に2段階で実行した。ビームが出力した `reverse_exact_UNKNOWN.txt` を GBFS に渡し、プロセス起動、前向き表構築、探索、結果の書出しを含めて測定した。外部コマンドによる追加の棋譜検証は計測外で実行した。3反復で方式の実行順を交互にし、分類の完全性、既存の確定結果の保持、各段階のカウンタと個別ベンチマークとの一致も検査した。

| 入力 | GBFS 単独の成功数 | 二段法の成功数 | GBFS 単独の時間 | 二段法の時間 |
|---|---:|---:|---:|---:|
| 独立96局面 | 54 | 54 | 11.233秒 | 11.429秒 |
| SAT 残存58局面 | 0 | 0 | 12.701秒 | 12.825秒 |

時間は3反復の中央値である。96局面では平均値で比較すると11.308秒と11.296秒となるため、小さな時間差を改善とも悪化とも強く解釈しない。一方、生成候補数の増加と成功数が増えないことは全反復で一致した。[実測の集計](pipeline_summary.json)、[96局面の各試行](holdout_pipeline.csv)、[58局面の各試行](legacy_sat_pipeline.csv)を参照できる。

### 前向き境界10石での確認

既存 CLI の `--discs` の既定値が10なので、主検証後に同じ入力と固定した設定で1反復の条件感度確認を行った。評価関数と幅の再選択はしていない。

| 入力 | GBFS の成功数 | ビームの成功数 | 二段法の生成数 / GBFS | 二段法の推計時間 / GBFS |
|---|---:|---:|---:|---:|
| 独立96局面 | 54 / 96 | 30 / 96 | 1.0187 | 1.0043 |
| SAT 残存58局面 | 0 / 58 | 0 / 58 | 1.0235 | 1.0187 |

10石境界でも全体の改善を確認できなかった。この表の時間は個別計測の加算であり、前節の CLI 全体の実測と区別する。

## 実装の検証

`cargo test --release --locked --offline` で193件のテストが成功した。追加した検査には、全評価関数と両方式の浅い全列挙との一致、絶対手番、パス、終局、標準初期配置以外の開始局面、幅制限後の `UNKNOWN`、候補生成上限、キャッシュ衝突、CLI の引数伝搬を含む。`estimate` のビーム出力を GBFS の入力として再読込みでき、設定欄のない過去の summary も読めることを検査した。[検証記録](verification.json)に要点を残した。

## 解釈と適用範囲

逆着手の分岐数が小さいことと、前向き境界へ到達しやすいことは同じではない。今回の評価はその違いを狙ったが、合法手数や同色隣接辺数だけでは、残すべき祖先候補を十分に選べなかったと考えられる。幅を狭めて得た低い生成数には、成功経路を捨てて早く終了した効果が含まれる。

この負結果は、すべての評価関数やビーム方式に対する不可能性の証明ではない。検証したのは `exact`、境界8石と10石、1スレッド、指定した予算である。対局から生成した局面は、一様に抽出した実現可能局面ではない。また、旧 SAT 入力への手番付与は新しい問い合わせを作っている。異なる入力分布、`equivalence`、並列度、大きい探索予算での改善をこの結果から主張できない。

したがって、今回の実装を速度改善として自動採用する根拠は得られていない。実験を続ける場合は、同じ判定数を維持した生成数・展開数・時間を評価し、より直接に境界への到達見込みを推定する評価を独立した入力で検証する必要がある。
