# 到達可能性ソルバの性能検証

このディレクトリは、コミット `9208dbd0f1981389de8086bdeb52490e56561226` と高速化後の実装を比較するための入力、測定結果、検証手順をまとめる。入力は性能と正しさを検査するためのものであり、到達可能局面数の統計的推計に使う一様標本ではない。

## 実測結果（採用版）

AMD EPYC 9V74、Rust 1.99.0、release ビルド、リポジトリ既定の `target-cpu=native` を使用した。別のビルドや測定を同時に走らせず、1ワーカー、旧版・新版の実行順を交互にして3回ずつ測定した。時間はプロセス起動、式や前向き表の構築、求解、結果出力を含む壁時計時間の中央値である。SAT の上限は終点候補ごとのソルバ呼出し1秒、逆探索は前向き境界8石・終点候補ごと10,000ノードとした。CPU の固定や周波数制御はしておらず、3反復を信頼区間の代用にはしない。

幾何対称性と色・手番交換を含む `equivalence` でも、全3反復で各入力の分類とノード数が一致した。各実行の合計は **15,335,814ノード** で、207件を NG、360件を UNKNOWN とした。`exact` と `equivalence` は異なる問い合わせなので、両者の確定件数を混同しない。

## 採用しなかった変更

Placement 符号化についても、開始・終了盤面を生成時に定数化する変更と、exactly-one の接頭辞 OR を片方向の逐次カウンタへ置き換える変更を試した。両方を含む試作版は45問の `placement` で中央値3.07秒から3.98秒へ遅くなり、`placement-columns` では制限時間内の OK が1件減った。変更を分けた比較でも、それぞれ時間切れの増加が見られた。そのため両方を撤回し、最終版の Placement 符号化本体は比較元と一致させた。追加した制約の全割当て検査は残した。

SAT の変数数や節数が減っても、変数番号・極性・伝播・探索順序の変化により求解時間は増え得る。採用判断では、式の大きさに加えて経過時間と確定件数を比較した。試作版と変更を分離した比較の数値も `measurements.json` に残している。

## 判定を維持する根拠

SAT の変更は、補助変数を除いたときに同じ合法手順を表す変形に限定した。

- Ply 符号化では、同じ捕獲パターンの `play AND capture` を表す変数を、反転する石の数だけ作る処理から1個を共有する処理へ変更した。旧変数はいずれも同じ論理式と等値なので、共有前後で手順に対する充足可能性は変わらない。
- Ply 符号化で同時に複数の手を選べない条件は、選択肢が6個以上のときに逐次カウンタで表す。真になった入力は接頭辞の補助変数を真にし、それより後の入力を禁止する。入力が高々1個だけ真である任意の割当ては、実際の接頭辞 OR を補助変数に割り当てれば拡張できる。したがって、条件を強めたり弱めたりしていない。
- 開始局面ですでに石のあるマスは、その後に空きマスへ戻らない。そのマスを着手先とする変数と捕獲パターンを省略する。反転先としての変数は残し、目標局面に含まれない空きマスへの合法手判定も残す。後者を省略すると、存在しない強制パスを許すおそれがある。
- Kissat への入力は、同じ順序の節とリテラルを1節ずつ変換して渡す。CNF 全体の中間コピーを作らず、変換用配列を再利用する。

逆探索の変更では枝を除外していない。通常の深さ優先探索は従来と同じ順序で候補を遅延生成し、探索深さに対応するフレームと1本の手順配列を持つ。順序付き探索は従来どおり全候補を整列するが、候補ごとの手順の複製を省く。反転を元に戻すマスクは、混合基数カウンタの変更した方向だけ更新する。着手点からの8本の射線は交差しないため、各方向の旧接頭辞と新接頭辞の XOR は、全方向の OR を再計算した結果と一致する。

探索順序に使う評価関数は、隣接した石の組をビット演算で数える。旧実装の整数除算と浮動小数点評価値を維持している。正確な局面キー、絶対手番、合法なパス、終局条件、探索上限に達したときの `UNKNOWN` は維持する。到達可能とする結果には、合法性を再検査した着手列が必須である。

これらの議論は今回の変更の正当性についてのものであり、既存実装や SAT ソルバ全体の形式検証ではない。SAT・逆探索による到達不能の判定は、完全な探索または完全な符号化に対する Kissat の UNSAT に依存する。有限個の回帰テストだけで全局面の無誤判定を証明したとは扱わない。

## LP の棄却を厳密に検査する

既存の LP フィルタは HiGHS の浮動小数点計算による `Infeasible` をそのまま棄却としていた。現在は双対レイを証明候補として取得し、元の制約に対する矛盾を任意精度整数で確認できた場合だけ棄却する。証明候補が得られない場合、証明候補が不正な場合、検証に失敗した場合は `Undetermined` として後段へ通す。不正な入力局面やソルバの実行エラーは、従来どおりエラーとして扱う。

行制約の係数を $a_i$、右辺を $b_i$、乗数を $y_i$ とする。$a_i x\ge b_i$ の行には $y_i\ge0$、$a_i x\le b_i$ の行には $y_i\le0$ を要求し、等式の乗数は任意とする。$c=\sum_i y_i a_i$、$d=\sum_i y_i b_i$ とすると、実行可能解は $c^\mathsf{T}x\ge d$ を満たす。一方、このモデルの変数はすべて $0\le x_j\le1$ を満たすので、$c^\mathsf{T}x\le\sum_j\max(c_j,0)$ である。したがって、

$$
d>\sum_j\max(c_j,0)
$$

を厳密に確認できれば実行不能である。有限の `f64` の値をビット列から正確な二進有理数として取り出し、全乗数に共通する正の2の冪でスケーリングして整数化する。モデルの係数と右辺も正確な整数であることを確認する。検証には許容誤差や近似的なゼロ判定を使わない。

この検査は、ソルバが返した証明候補に数値誤差があっても、誤って棄却しないためのものである。到達可能局面が元の緩和モデルを満たすという性質は引き続き前提となる。HiGHS は双対レイの取得時に再求解する場合があるため、棄却する局面の処理に追加の時間がかかる。`run_filters lp --ip` でも、整数条件だけに由来する実行不能性は連続緩和の証明書で検証できないため、別の証明書を持たない場合は未確定として通す。

`result/thesis_layer_sat/lp_NG.txt` の1,024局面に黒手番を付けて比較したところ、全3反復で旧版は1,024件を棄却し、新版は1,021件を厳密な証明付きで棄却し、3件を未確定として通した。未確定になったのは元ファイルの421・546・913行目で、双対レイが厳密検証を通らなかった。この結果から、旧版の分類そのものが誤っていたとは結論しない。

単一ワーカーでの中央値は **4.695秒から18.812秒** で、約4.01倍の処理時間になった。これは無誤判定を優先するために加えた検証の費用であり、高速化として数えない。LP を含むパイプライン全体の速度比は別途測定が必要である。全入力の検証結果と理由は [results/lp-candidate-results.csv](results/lp-candidate-results.csv) に保存する。

LP の測定バイナリは厳密検証を追加した時点のものを使った。その後に変更した Placement 符号化は LP の実行経路に含まれず、LP のソースは採用版と一致する。両ビルドのコミット対応と測定バイナリのハッシュは `measurements.json` の `lp_exact_certificate_cost` に区別して記録した。

## 検証する条件

既存の配列型オセロ実装は、SAT の変数生成器や高速ビットボード実装を使わずに合法手とパスを計算する。回帰テストは、小規模な全列挙、幾何対称性、絶対色と手番の交換、任意の開始局面、先頭・途中・末尾の強制パス、終局からの不正なパスを含む。

追加したテストでは、逐次カウンタの入力と補助変数の全割当てを調べる。逆探索は旧実装と分類だけでなく着手列・探索ノード数・上限停止も比較する。評価関数は全2マス配置と4,096個の乱数盤面で旧計算とビット単位で比較し、候補生成器は既存の独立した全列挙と照合する。

`scripts/bench_reachability.py` は、両版の実行順を交互にし、壁時計時間、各分類の件数、SAT 変数数・節数、式の生成時間・ソルバ側の時間を記録する。両版または反復間の OK/NG の矛盾、入力の欠落・重複、既知の正解との矛盾があれば失敗する。すべての OK 証跡を独立した Python の配列型ルールで再生する。UNKNOWN と確定結果の変化は、誤判定と混同せず別に報告する。

採用版では `cargo +1.99.0 test --release --locked --offline -j4 -- --test-threads=2` が **192件成功、失敗0件、無視0件** で完了した。全22グループの出力は [results/tests.log](results/tests.log)、ソースの Git tree・コンパイラ・実行ファイル・ログのハッシュは [validation.json](validation.json) を参照。

採用版の比較で返された着手列はすべて独立再生し、重複を除いた44本を [results/certificates.csv](results/certificates.csv) に保存した。各手順と元の実行の対応も同じディレクトリに記録している。最終比較と同値類モードの予備比較を合わせた44実行では、異なる確定問い合わせ465件について OK/NG の矛盾は0件だった。反復や異なるソルバでの同じ問い合わせを別の局面として数えない。
